### Autopay

- New feature on the subscription detail screen: shows whether autopay looks enabled for that subscription. Same no-API-access limitation as Pause/Cancel/Change Plan -- there's no way to check a provider's real autopay status, so it assumes the industry-standard default (on) via `tracked_subscriptions.autopay_enabled boolean not null default true`, and only flips to false once the user confirms (via a button) that they've actually disabled it themselves on the provider's billing page. "Disable Autopay" opens that billing page the same way Pause/Cancel/Change Plan already do.
- Added "Manage via UPI App" (`lib/upiApps.ts`, `components/UpiAppPicker.tsx`) since many Indian autopay mandates are actually controlled by the UPI app (GPay/PhonePe/Paytm/BHIM), not the merchant. Opens the chosen app via its custom URL scheme (Play Store fallback if not installed) -- there's no public deep link into any of these apps' Autopay/Mandates screen for a specific merchant, so it only opens the app itself with an in-app instruction to find Autopay/Mandates manually. `phonepe://`/`paytmmp://` are well-established schemes; `gpay://`/`bhim://` are unverified and need confirming on a real device.
- Standalone-APK verification (build → download → binary-grep the compiled bundle for expected strings) is now the standard way features get confirmed working in this project, not dev-client reload testing -- reload-based testing repeatedly failed to reflect real code state this session (a stray Metro instance silently landing on the wrong port was the last confirmed cause), while the binary-grep approach caught real bugs directly (e.g. the missing EXPO_PUBLIC_* env vars on the `preview` EAS environment) with certainty. Also set up `npx expo start --web` for fast JS-only UI iteration (fetch + grep the plain-text web bundle directly, no binary tricks needed) -- native-only behavior (UPI app Linking calls) still needs a real APK.
- Followed up on PhonePe's own Autopay screen specifically (per a real screenshot the user sent showing it) with four separate research passes, including PhonePe's official developer docs (their "Customized Deeplink" API) -- confirmed conclusively that no UPI app publishes any way to deep-link into an existing mandate's management screen, not merchant-specific and not even the generic list; the one real improvement available was cutting the extra "pick an app" tap by making PhonePe the one-tap default action, with other apps as a fallback.

### Renewal reminder

- New feature: a "Renewing soon" banner on Home (`components/RenewalReminderBanner.tsx`) plus a highlighted Next Payment row on the subscription detail screen, both firing when a subscription's `next_renewal_date` is within `lib/businessDays.ts`'s 2-business-day window (Saturday/Sunday-aware, no public-holiday calendar -- not worth the yearly upkeep for a soft reminder).
- This is an in-app banner, not a push notification -- true push (working while the app is closed) needs `expo-notifications` (a new native module → another EAS rebuild) plus a server-side scheduled job, deliberately not scoped in without asking first.
- The real blocker this surfaced: `tracked_subscriptions.next_renewal_date` was `null` for every single row in the live database, because the Gmail-approve flow (`useDetectedSubscriptions.approve()`) had always hardcoded it to `null` -- no reminder feature could have worked without fixing that first. `gmail-scan-subscriptions` now also extracts a charge date from the receipt (`guessChargeDate`, same "simple heuristic, not a real parser" caveat as `guessAmount`/`guessBillingCycle`) and projects it forward to the next future occurrence (`projectNextRenewal`) via the billing cycle, stored as `detected_subscriptions.guessed_next_renewal_date` and carried through into `tracked_subscriptions.next_renewal_date` on approve. Still strictly scoped to the existing `KNOWN_SENDERS`-filtered Gmail query -- nothing new was added that reads outside that curated sender list.
- Added a bell icon in Home's header (`components/RenewalBell.tsx`), a persistent always-visible companion to the banner -- carries a red dot when something's within the reminder window, tapping it shows the exact next billing date(s) in a bottom sheet. Both the bell and the banner share one `getUpcomingRenewals()` (`lib/renewalReminders.ts`) so they can never disagree about what counts as "soon."
- SMS delivery for these reminders was considered and dropped for now: confirmed via research that TRAI (India's telecom regulator) mandates DLT registration -- business entity, sender ID, and pre-approved message templates -- for every SMS sender regardless of provider, free or paid; without it, messages are silently dropped at the network level with no error. The user chose to defer this rather than build against a provider that can't actually deliver yet. `expo-notifications`-based push (genuinely free, no equivalent regulatory burden, but needs a new native module → EAS rebuild) was offered as the realistic alternative if a proactive-outside-the-app notification is wanted later.
- Found and fixed a real bug in `lib/businessDays.ts`: `new Date("2026-09-30")` (a bare date string) parses as UTC midnight, not local midnight -- a classic JS trap that can silently land on the wrong local calendar day depending on the runtime's timezone handling. Directly tested the old logic in a confirmed IST environment and it happened to compute correctly there, which is exactly why it wasn't safe to trust it behaved identically in Android's Hermes engine on a real device -- replaced with explicit year/month/day parsing (`parseLocalDate`) that's never ambiguous, regardless of runtime.

- Found a second, more serious bug while investigating that same account: the 58 "pending" candidates were mostly noise, not real subscriptions -- 25 were Spotify's own upsell emails ("Get Spotify Premium... ₹799") and marketing newsletters (concert/tour announcements from an unrelated artist-updates list), 17/15/1 were similar non-receipt mail from Adobe/ChatGPT/Dropbox. `gmail-scan-subscriptions` matched on sender domain alone with no check for whether an email was actually a receipt, so a real subscriber's real receipt was getting buried under dozens of false positives (which is also why "next payment date isn't generated" -- there's no charge date in a concert-tour email). Also swept the account's existing pending candidates with the same rule (`status = 'dismissed'` for anything that doesn't match) -- 57 of 58 were junk; the one survivor is a genuine, previously-undetected Spotify receipt.

### Gmail scan -- removing the 8-domain limit

- Cleaned up harikiran594@gmail.com's already-tracked Netflix subscription (₹649/mo): it had been approved from a batch of 18 emails that predated `looksLikeReceipt()` and none were actual receipts (6 login-OTP codes, 4 content recommendations, 2 win-back emails, 1 account-sharing notice, the rest vague one-liners) -- deleted both the `tracked_subscriptions` row and the 18 underlying `detected_subscriptions` rows. It will not resurface on a rescan unless a genuine receipt email exists in the inbox that hasn't been found yet.
- User asked how far back the scanner actually looks -- it was capped at `newer_than:90d` *and* a hard `maxResults: 100` with no pagination, on top of being restricted to 8 curated sender domains (`KNOWN_SENDERS`). Any of the three could hide a real subscription.
- Built a temporary, read-only diagnostic endpoint (`gmail-diagnostic-dump`, deployed with `--no-verify-jwt`, took a plain `user_id` query param, wrote nothing to any real table) to see what a real inbox actually contains outside the curated domains: `category:purchases` (Gmail's own Purchases-tab classifier) plus a broad subscription/receipt keyword search, 365-day window, up to 500 messages. Ran once against harikiran594@gmail.com, saved the full raw dump to `harikiran_subscription_scan_review.txt` at the project root for manual review, then deleted the endpoint (an unauthenticated any-user-by-id Gmail reader is not something to leave deployed).
- Two things fell out of that dump: (1) a real, previously-invisible subscription -- Claude Pro via Google Play billing, ₹1999/month, renewing through `google.com`, a domain nowhere on the old 8-domain list; (2) proof that `looksLikeReceipt()` alone is unsafe once the domain restriction is gone -- Uber ride receipts, Zomato food-order confirmations, one-off Amazon purchases and Razorpay donations are all genuinely receipt-shaped (order confirmation / payment successful / charged wording) without being subscriptions at all.
- Rewrote `gmail-scan-subscriptions` accordingly: query is now `category:purchases OR subscription OR "auto-renew" OR renewal OR membership OR recurring OR receipt OR invoice OR billed OR charged`, no domain restriction, window widened to 180 days, pagination added up to a 200-message cap (a real scan runs synchronously in one HTTP request, so an uncapped diagnostic-style crawl that took minutes and hit Gmail API rate limits isn't viable here). `KNOWN_SENDERS` is now just a "give this a clean curated name/logo" fast path, not a filter. For anything NOT on that curated list, insertion now requires a *second* gate, `hasSubscriptionEvidence()` (subscription/membership/renew/recurring wording), in addition to the existing `looksLikeReceipt()` gate -- this is what keeps Uber/Zomato/Amazon/Razorpay out while still letting Google Play's genuinely subscription-worded renewal/receipt emails through. Also had to strip `SUBSCRIPTION_NOISE_RE` (the "manage your email subscription preferences" / "unsubscribe" footer boilerplate present on nearly every commercial email) before testing for subscription wording, confirmed necessary because Uber promo mail and LinkedIn digests were otherwise passing that gate on footer text alone.
- Found (via the same account) that Magnific's own receipt email never got fetched at all -- only the user's own self-forward of it did, mislabeled as "Hari Kiran" in the review queue since the sender was the user's own address. Root cause: on a transaction-heavy real inbox, everyday Uber/Zomato/Amazon/Swiggy/BigBasket/Instamart/Razorpay mail alone made up a large share of every match, crowding an older genuine subscription receipt out of the 200-message scan budget entirely (confirmed by finding 5 Uber "pending" false-positive rows already sitting in this account's real review queue -- all Uber One marketing, zero real subscriptions). Added `NOISY_NON_SUBSCRIPTION_DOMAINS` (`-from:` exclusions for those specific domains) to the query -- curated senders are still always ORed back in unconditionally, so nothing legitimate can be excluded by this, it just stops near-zero-yield transactional volume from eating the scan budget. Manually relabeled the existing mislabeled row from "Hari Kiran" to "Magnific".
- User reported Spotify/Claude/Gemini specifically "not fetching" despite being real subscriptions. Root cause was one bug (billing-intermediary mislabeling) plus one genuine gap (a date-format the parser didn't handle), not a fetch failure:
  - **Google Play mislabeling**: every subscription billed through Google Play shares the same sender display name ("Google Play"), so grouping-by-service-name was silently merging THREE unrelated real subscriptions -- Claude Pro (₹1999/mo), Google One/Gemini (Google AI Pro 5TB), and an unrelated fitness app (BodBot, ₹230/yr) -- into one wrongly-labeled "Google Play" tracked subscription, with only Claude's price surviving into the merged row. Added `PRODUCT_NAME_HINTS` (body-content overrides for well-known Play-billed products: Claude, Google One/Gemini, YouTube Premium) plus `GOOGLE_PLAY_MERCHANT_RE`, a generic extractor for "subscription ... from X on Google Play" wording, so any other Play-billed app (like BodBot) gets its own real name instead of collapsing into the reseller's name. This only changes naming/icon, never the receipt/subscription gating, which still depends solely on the real sender domain. Manually split the existing bad data apart: deleted the wrongly-merged tracked row, relabeled its 6 underlying `detected_subscriptions` rows into their correct 3 services, and reset them to `pending` for the user to re-approve individually.
  - **Spotify's date parser**: `guessChargeDate` only understood "26 September 2026" (day-first) ordering; Spotify's real receipt says "Date September 26, 2026" (month-name-first), so its charge date silently never matched at all. Added `MONTH_NAME_FIRST_RE` for that ordering. First attempt used a greedy `\D{0,10}` gap between "date" and the month name, which backtracks INTO the month name itself (`\D` still matches letters) -- confirmed by directly testing it against the real receipt text, it captured "ber" out of "September" and produced an Invalid Date. Fixed by restricting the gap to `[^\w]{0,5}` (non-word characters only), which can't eat into the word.
  - Also found and fixed a related bug this surfaced: a "Welcome to Netflix" signup email (only in the queue via the known-sender `LIFECYCLE_RE` fallback) contains a plan-comparison table with real-looking prices ("Basic ₹149, Standard ₹649...") -- `classifyEvidenceTier` was giving this tier 1 ("confident, priced evidence") purely because a price/date was found, with no check that the email was actually a receipt. `guessAmount`/`guessChargeDate` are now only ever called when `isReceipt` is true, and tier 1 now requires `isReceipt` as well, not just a found amount/date on its own -- a signup/lifecycle-only email can surface (still useful, since a real subscription with zero receipt evidence needs some way to appear) but can never masquerade as a confident, priced detection.
- Two follow-up bugs: (1) Netflix still wasn't showing even after the domain-limit fix -- checked and confirmed this account genuinely has zero receipt-shaped Netflix emails anywhere (17 matched across netflix.com/members.netflix.com/account.netflix.com, all sign-in codes/content recs/a signup welcome email). Added `LIFECYCLE_RE` (welcome/signup/cancellation wording) as a fallback gate that only applies to curated `KNOWN_SENDERS` -- a trusted service can now be listed for manual review from a signup/cancellation email alone (no guessed price, same as any other blank-price candidate), instead of staying permanently invisible just because its own receipts don't land in this inbox. (2) The review card's "×N" badge for a multi-email group had no way to see what those emails actually were -- added `app/(tabs)/subscriptions/detected-group.tsx`, opened by tapping the badge or the "N emails -- tap to see" line, listing every email in the group (evidence tier + plain-language meaning, guessed amount/date, and the actual source snippet) instead of only ever showing the single best one on the main card.
- Added `detected_subscriptions.evidence_tier` (1 best -- 4 weakest, `classifyEvidenceTier` in the edge function, computed at both insert and rescan-refresh time): tier 1 is an actual receipt with a real amount and/or charge date, tier 2 is a redeem/claim/trial-ending/payment-declined nudge, tier 3 is a bare subscribe/upgrade invitation, tier 4 is everything else that still cleared both detection gates. `useDetectedSubscriptions` now sorts each service's group by tier (not just "has an amount") and merges complementary fields from the rest of the group into the single best-tier item shown on the review card (e.g. borrows a renewal date from a different email in the group if the top-tier one doesn't have it) -- one card per service, as informative as the group collectively allows, not just whatever the single newest or single priced email happened to contain.

### Home currency defaults from phone number, not hardcoded USD

- `profiles.home_currency` is `not null default 'USD'` at the DB level, so Insights (and the "X/mo total" line) showed a literal $ for anyone who never happened to open the currency picker in Settings, regardless of what they actually pay in.

Updated the test account's stored phone number to include its real "+91" prefix (confirmed from its own Razorpay receipts earlier this session) so the auto-correction will take effect on its next profile load.
